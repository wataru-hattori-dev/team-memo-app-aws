## 1. 全体方針・スコープ

### 1.1 方針

- **ローカル完結を最優先**する。フロント（Vite）+ SAM Local + DynamoDB Local で Phase 1〜4 を通し検証し、合格まで実 AWS デプロイは行わない。
- **Phase スライス順を厳守**する。依存関係は 作成 → 一覧 → 詳細／更新 → 削除。各 Phase で API・UI・例外・テスト観点をまとめて満たしてから次へ進む。
- **現行 IaC（`template.yaml`）を正本**とし、エンドポイント追加・スキーマ変更は必要最小限に抑える。変更が必要な場合は `docs/spec.md` まで遡って整合させる。
- 実装は **実装計画書（ステップ 4）完了後**に着手する。本ドキュメントでは方針・分担・リスク・未決のみを固定する。

### 1.2 スコープ（In）

| 区分 | 内容 |
|------|------|
| 機能 | Phase 1 新規作成、Phase 2 一覧、Phase 3 詳細・更新、Phase 4 削除（画面同期含む） |
| API | `POST /memos`、`GET /memos`、`PUT /memos/{memoId}`、`DELETE /memos/{memoId}` |
| UI | React + TypeScript（strict）+ Tailwind。API 呼び出しは `frontend/src/api/` に集約 |
| データ | DynamoDB `memoId` PK。属性は要件定義書 1.4 のとおり |
| 検証 | ローカル E2E（受け入れ最低ライン: 要件 T-01〜T-04） |
| 実環境の画面 | 非公開 S3 + CloudFront（OAC、HTTPS）。手順は `docs/build.md` §8。API 認証は付けない |

### 1.3 スコープ外（Out）

要件定義書 2.2 および基本仕様のスコープ外に従う。

- 認証・認可（Cognito / JWT 等）の実装
- 全文検索用 GSI、添付・リアルタイム同期
- CI/CD、カスタムドメイン
- ソートキー／GSI／LSI の追加

### 1.4 入力ドキュメントとの整合確認

| 観点 | 結論 |
|------|------|
| API 4 操作・パス | 要件・spec・`template.yaml` で一致 |
| 単一 Lambda・Python 3.11・`MEMOS_TABLE_NAME` | 一致 |
| CORS | 既定は開発向け `*`。実環境は `CorsAllowOrigin` を CloudFront の URL に合わせる（`docs/build.md` §8） |
| `GET /memos/{memoId}` | IaC／spec に無し。要件では不明点（U-08）。本 Plan で仮置き（後述） |
| AGENTS.md §7「現在ステップ」 | 古い記述が残存。作業実態はステップ 3。実装計画以降で AGENTS 更新を検討可 |

矛盾により本 Plan を止める事項はない。未決は §8 および仮置き方針で扱う。

## 2. アーキテクチャ／技術アプローチ

### 2.1 論理構成（維持）

```text
[ブラウザ / Vite :5173]
    │  VITE_API_BASE_URL → http://127.0.0.1:3000
    ▼
[SAM Local / API Gateway]  /memos , /memos/{memoId}
    ▼
[Lambda MemosFunction]  app.lambda_handler（メソッド・パス分岐）
    │  MEMOS_TABLE_NAME / DYNAMODB_ENDPOINT_URL
    ▼
[DynamoDB Local :8000]  PK: memoId
```

実環境でも同一の論理構成（API Gateway REST + 単一 Lambda + DynamoDB）を前提とするが、**デプロイはローカル E2E 合格後**とする。

### 2.2 バックエンド方針

| 項目 | 採用方針 | 選択肢と比較した理由 |
|------|----------|----------------------|
| 関数構成 | **単一 Lambda**（現行 IaC） | 分割は運用・ローカル起動が複雑になる。CRUD 規模では単一で十分 |
| ルーティング | イベントの HTTP メソッド＋パスで分岐 | API Gateway プロキシ統合の標準パターン |
| DynamoDB アクセス | boto3／Resource。テーブル名は環境変数のみ | AGENTS／spec と一致。ハードコード禁止 |
| 一覧取得 | **Scan（全件）** | GSI なし・フィルタなし（U-02 仮置き）。小規模チームメモ向け |
| ID 生成 | **UUID（文字列）**（U-12 仮置き） | 分散・衝突耐性。形式はサーバ固定 |
| 日時 | ISO 8601（UTC 想定）をサーバが付与 | `createdAt` は作成時のみ、`updatedAt` は作成・更新で設定 |
| 依存パッケージ | 標準＋boto3 中心。追加は必要最小限 | Lambda ランタイムに boto3 あり。過剰なフレームワークは避ける |

### 2.3 フロントエンド方針

| 項目 | 採用方針 | 理由 |
|------|----------|------|
| ブートストラップ | Vite で React + TS + Tailwind を `frontend/` に構築 | AGENTS／要件どおり |
| API 層 | `frontend/src/api/` にクライアント集約。型は `types/` | URL 散在防止。Phase 追加時も拡張しやすい |
| 画面構成（方針） | 一覧を基点に、作成・詳細／編集・削除へ導線 | Phase 2 の UI-P2-05、Phase 依存に整合 |
| 状態 | 画面／機能単位のローカル状態で開始。過剰な状態管理ライブラリは初期不要 | 規模に対してシンプル。必要になったら実装計画で再評価 |
| 作成後遷移 | **一覧へ戻る／一覧を再表示**（U-13 仮置き） | Phase 1→2 の流れと受け入れ（作成結果が一覧で見える）に直結 |

### 2.4 API セマンティクスの仮置き（要件不明点の方針化）

詳細なバリデーション数値・エラーコード表は実装計画で表に落とす。ここでは **仮置き方針** を明示する。

| ID | 仮置き方針 | 備考 |
|----|------------|------|
| U-01 | **認証なし**（現行 IaC・O-01） | 導入時は要件再定義 |
| U-02 | **フィルタ・ページングなし（全件）** | 件数増大時は後続で再設計 |
| U-03 | **必須は非空文字列（`title`/`body`/`author`）。最大長は実装計画で数値仮置き** | 厳密値は未決のまま「要確認」も可（§8） |
| U-04 | エラー JSON は **`{ "message": "<説明>" }` を最小共通形** | コード体系は後続拡張可 |
| U-05 | DELETE 成功は **`204 No Content`（ボディなし）** | フロントはステータスで成功判定 |
| U-06 | PUT は **クライアント指定フィールドの全置換**（`title`/`body`/`author` 必須）。`memoId`/`createdAt` は変更しない | PATCH 相当は初期スコープ外 |
| U-07 | 一覧の表示順は **サーバ非保証**。UI 側で `updatedAt` 降順ソートを推奨 | Scan 順に依存しない |
| U-08 | **`GET /memos/{memoId}` は初期追加しない**（現行 IaC 維持）。詳細は一覧選択時のクライアント状態、および更新レスポンスで表示。直リンク／リロード時は一覧再取得後に該当件を探すか、一覧へ戻す | 不足が明確なら IaC＋spec 更新で単一取得を追加 |
| U-09 | 削除前に **簡易確認（ダイアログ等）を置く** | 誤削除防止。必須 UI |
| U-10 | 性能・件数上限の数値目標は **初期未定義** | ローカル小規模想定。上限が必要になったら要件更新 |
| U-11 | 同時更新は **最後の書き込み優先**（楽観ロックなし） | NFR-11 未定義への仮置き |
| U-12 | `memoId` は **UUID 文字列** | テスト・イベントも同形式を想定 |
| U-13 | 作成成功後は **一覧へ遷移または一覧を再表示** | 詳細直行は U-08 仮置きと相性が悪いため初期は一覧優先 |

### 2.5 Phase 別アプローチ（方針レベル）

| Phase | バックエンド焦点 | フロント焦点 | 検証のゴール |
|-------|------------------|--------------|--------------|
| 1 新規作成 | `POST`、サーバ生成属性、4xx/5xx | 入力画面、保存、成功／失敗表示、api 層の土台 | UI から 1 件作成でき DynamoDB に残る |
| 2 一覧 | `GET`、0 件空配列、Scan | 一覧・空状態、Phase 3/4 への入口 | 作成済みが並び、空状態が分かる |
| 3 詳細・更新 | `PUT`、404、`updatedAt` 更新 | 詳細表示・編集・同期（U-08 仮置きに従う） | 更新が永続化し UI に反映 |
| 4 削除 | `DELETE` 204/404 | 確認ダイアログ、削除後の一覧／詳細同期 | 削除後に画面から消え、失敗時は消えない |

横断: CORS（OPTIONS 含む）、共通エラー応答形、環境変数による DB 向き先。

## 3. モジュール／レイヤ分担（方針レベル）

疑似コードやファイル単位の詳細タスクは書かない。実装計画書で分解する。

### 3.1 バックエンド（`src/memos/`）

| レイヤ（論理） | 責務 |
|----------------|------|
| エントリ（`app.lambda_handler`） | イベント受付、メソッド／パス分岐、レスポンス組み立て |
| バリデーション | Body／パスの必須・型・（仮置き）制約。不正時は 4xx |
| ドメイン／ユースケース | 作成・一覧・更新・削除の業務ルール（ID・日時・不存在） |
| データアクセス | DynamoDB put／scan／update／delete。テーブル名・エンドポイントは環境変数 |
| 共通レスポンス | 成功 JSON、`message` 付きエラー、ステータスと `Content-Type` |

初期は単一パッケージ内のモジュール分割で足りる想定。Layer／`src/common/` は共有要件が出てから検討する。

### 3.2 フロントエンド（`frontend/`）

| 領域 | 責務 |
|------|------|
| `api/` | `VITE_API_BASE_URL` 基準の HTTP 呼び出し。Phase ごとの API 関数 |
| `types/` | メモ属性・エラー形の TypeScript 型 |
| 画面／コンポーネント | 作成フォーム、一覧、詳細／編集、削除確認。表示と操作に専念 |
| アプリシェル | 画面切替またはルーティング方針（実装計画で具体化。過剰なルータ必須ではない） |

### 3.3 IaC・付帯

| 領域 | 責務 |
|------|------|
| `template.yaml` | API／Lambda／Table／CORS／非公開 S3／CloudFront。単一取得 API（U-08）は追加しない |
| `events/` | `sam local invoke` 用イベント（Phase ごとの代表ケース） |
| `tests/` | バックエンド単体／統合の置き場。具体ケースは実装計画 |
| `docs/build.md` | ローカル起動・ビルド・実 AWS デプロイ手順の正本 |

### 3.4 責務境界

- フロントから DynamoDB へ直接アクセスしない。
- コンポーネントから API URL を直書きしない。
- Lambda 内にフロント向け UI ロジックを持たない。
- 秘密情報はリポジトリに置かない（`.env` / `.env.local` + gitignore）。

## 4. ローカル開発・検証方針

### 4.1 推奨構成

| コンポーネント | 目安 |
|----------------|------|
| DynamoDB Local | ポート `8000`。開発中は実アカウント DynamoDB を使わない |
| SAM Local API | `sam local start-api`、ポート `3000`。`--env-vars` で `DYNAMODB_ENDPOINT_URL` 等を注入 |
| Vite | `frontend/` で `npm run dev`、ポート `5173`。`VITE_API_BASE_URL` は SAM Local |

Windows 環境では Docker 経由の DynamoDB Local と `host.docker.internal` の到達性を初期セットアップで確認する。

### 4.2 段階的スライス検証

各 Phase 終了時に、次をローカルで確認してから次 Phase に進む。

1. **API**: SAM Local に対し、当該 Phase のメソッドが要件のステータス／JSON を返す（正常・代表的異常）。
2. **永続化**: DynamoDB Local 上で作成・更新・削除の結果が期待どおり。
3. **UI**: Vite から当該 Phase の操作が完了し、成功／失敗が利用者に分かる。
4. **CORS**: ブラウザからクロスオリジン呼び出しが可能。

Phase 4 完了後に **横断 E2E**（作成→一覧→詳細／更新→削除）と受け入れ T-01〜T-04 を確認する。

### 4.3 テスト手段の方針（詳細は実装計画）

| 手段 | 使い方 |
|------|--------|
| `events/` + `sam local invoke` / start-api | API の早期・回帰確認 |
| `tests/` | バリデーション・分岐の単体。可能なら DynamoDB Local 向け統合 |
| 手動 UI E2E | Phase ごとおよび最終通し。自動化は初期必須としない |

Phase 0〜E の受け入れ確認はローカル E2E のままとする。本番相当の負荷試験は本 Plan の対象外。デプロイ手順は `docs/build.md` §8。

## 5. リスクと対策

| ID | リスク | 影響 | 対策 |
|----|--------|------|------|
| R-01 | 一覧が Scan 全件のため件数増で遅延・コスト増 | Phase 2 以降の実用性 | 初期は小規模前提（U-02/U-10）。必要時にページング／GSI を要件から再設計 |
| R-02 | 単一取得 API なし（U-08）で詳細の直リンク・再読込が弱い | Phase 3 UX | 仮置きどおり一覧起点。不足が明確なら `GET /memos/{memoId}` を IaC＋spec＋要件へ追加 |
| R-03 | PUT 全置換／部分更新の解釈ブレ | データ破壊・テスト不一致 | U-06 を `docs/spec.md` §6.2 の入出力例で固定 |
| R-04 | DynamoDB Local ↔ SAM Local（Docker）接続失敗（特に Windows） | 全 Phase 停止 | 初期に接続確認手順を実装計画／scripts に含める。`DYNAMODB_ENDPOINT_URL` を明示 |
| R-05 | CORS／OPTIONS 不備 | ブラウザ E2E 不可 | IaC の CORS を前提に、Phase 1 の最初のブラウザ呼び出しで確認 |
| R-06 | 認証なしの API を実環境に出す | URL を知っていればメモの閲覧・変更・削除ができる | 画面バケットは非公開（CloudFront 経由のみ）。API の認証は未導入。範囲を限るときは認証を要件から再定義（U-01） |
| R-07 | 同時更新の上書き（U-11） | 他者の編集消失 | 初期は許容。必要なら版／条件付き更新を後続 |
| R-08 | 削除成功後の UI 非同期（E-P4-03） | 受け入れ失敗 | 成功時のみ一覧再取得または状態から除去。失敗時は画面を消さない |
| R-09 | バリデーション未確定（U-03）による手戻り | API／UI／テスト | 仮置き＋実装計画で数値を明示。確定値が変われば要件へ反映 |
| R-10 | ドキュメントと IaC の乖離 | 手戻り | API／リソース変更時は spec → 要件 → plan の順で更新 |

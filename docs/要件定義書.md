## 1. 機能概要 / 目的

### 1.1 目的

チーム内でメモ（タイトル・本文・作成者）を共有し、ブラウザ上から作成・一覧・詳細／更新・削除できる Web アプリケーションを提供する。

### 1.2 機能概要（Phase 対応）

| Phase | 機能 | 範囲 | 対応 API |
|-------|------|------|----------|
| Phase 1 | 新規作成 | 入力画面〜保存処理まで | `POST /memos` |
| Phase 2 | 一覧表示 | 取得処理〜一覧画面表示まで | `GET /memos` |
| Phase 3 | 詳細・更新 | 詳細画面・編集〜更新処理まで | `PUT /memos/{memoId}`（詳細取得の手段は不明点） |
| Phase 4 | 削除 | 削除処理・画面の同期まで | `DELETE /memos/{memoId}` |

横断要件として、ローカル E2E（フロント + SAM Local + DynamoDB Local）で Phase 1〜4 を通して検証できること。

### 1.3 成功の定義（受け入れの大枠）

ローカル環境（`http://localhost`）において、利用者が Phase 1〜4 の操作を UI 経由で完了でき、かつバックエンド API が本要件どおりの HTTP ステータスと JSON を返すこと。実 AWS へのデプロイ完了は受け入れ条件に含めない。

### 1.4 共通データ属性

全 Phase で扱うメモ属性は次のとおり。

| 属性 | 必須 | 生成／更新 | 説明 |
|------|------|------------|------|
| `memoId` | はい | 作成時にサーバ生成 | 一意 ID。パスパラメータと一致 |
| `title` | はい | クライアント指定（作成・更新） | タイトル |
| `body` | はい | クライアント指定（作成・更新） | 本文 |
| `author` | はい | クライアント指定（作成・更新） | 作成者／名前 |
| `createdAt` | はい | サーバ生成（作成時）。更新では変更しない | ISO 8601 文字列 |
| `updatedAt` | はい | サーバが作成・更新時に設定 | ISO 8601 文字列 |

### 1.5 共通 API／UI 方針

| 項目 | 要件 |
|------|------|
| ランタイム | 単一 Lambda（`MemosFunction`）が HTTP メソッド・パスで分岐。レスポンスは JSON。削除成功は `204`（ボディなし）。入出力例は `docs/spec.md` §6.2 |
| Content-Type | `application/json`（ボディあり応答時） |
| CORS | フロント（Vite: `http://localhost:5173` 等）からの呼び出しを許可。`OPTIONS` を含む |
| API 集約 | フロントの API 呼び出しは `frontend/src/api/` に集約する |
| API ベース URL | `VITE_API_BASE_URL` で切替。開発時の既定は SAM Local（例: `http://127.0.0.1:3000`） |
| UI 技術 | React + TypeScript（`strict`）+ Tailwind CSS。巨大 CSS フレームワークは追加しない |

## 2. 前提・対象外

### 2.1 前提

| ID | 前提 |
|----|------|
| P-01 | IaC 正本はリポジトリルートの `template.yaml` である |
| P-02 | バックエンドは AWS SAM / Lambda（Python 3.11）単一関数で CRUD を処理する |
| P-03 | データストアは DynamoDB（ローカルは DynamoDB Local）。テーブル PK は `memoId`（String） |
| P-04 | フロントエンドは `frontend/` 配下に完結する |
| P-05 | 開発はローカル完結優先。ローカル E2E 合格まで実 AWS デプロイは行わない |
| P-06 | API は REST。パスは `/memos` および `/memos/{memoId}` |
| P-07 | 認証なし（`template.yaml` に Authorizer なし）を初期前提とする（要否は不明点） |
| P-08 | 文字コードは UTF-8 |
| P-09 | 本要件は Phase 1→2→3→4 の順で満たすことを想定する（依存: 作成→一覧→詳細／更新→削除） |
| P-10 | 実環境の画面は非公開 S3 + CloudFront（OAC、HTTPS、`index.html`）。API の認証は付けない。CORS の既定は `*` で、デプロイ後に CloudFront の URL のみへ絞る。手順は `docs/build.md` §8 |

### 2.2 対象外

| ID | 対象外 |
|----|--------|
| O-01 | ユーザー認証・認可（Cognito / JWT 等）の実装（導入時は要件を再定義） |
| O-02 | メモの全文検索用 GSI |
| O-03 | 添付ファイル・画像アップロード |
| O-04 | リアルタイム同期（WebSocket 等） |
| O-05 | CI/CD パイプライン |
| O-06 | カスタムドメイン（画面は CloudFront の既定ドメイン、API は execute-api の URL） |
| O-07 | ソートキー／GSI／LSI の追加 |

実 AWS へのデプロイ手順の正本は `docs/build.md` §8 である。

## 3. Phase 1：新規作成機能（入力画面〜保存処理まで）

### 3.1 概要

利用者が入力画面でタイトル・本文・作成者を入力し、システムがメモを永続化して一意 ID と日時を付与する。

### 3.2 ユースケース（正常系）

#### UC-P1-01 メモを新規作成する

| 項目 | 内容 |
|------|------|
| アクター | チームメンバー（ブラウザ利用者） |
| 事前条件 | API・DB・フロントが起動している |
| 基本流れ | 1. 利用者が新規作成の入力画面を開く<br>2. タイトル・本文・作成者を入力する<br>3. 保存操作を行う<br>4. システムが `POST /memos` で保存し、`memoId` / `createdAt` / `updatedAt` を付与する<br>5. 作成結果が UI に反映される（作成済み内容の表示、または一覧への遷移／反映） |
| 事後条件 | DynamoDB にメモが 1 件存在する。サーバ生成属性が設定されている |

### 3.3 API 要件

| 項目 | 要件 |
|------|------|
| メソッド／パス | `POST /memos` |
| リクエスト Body | `title`, `body`, `author` 必須 |
| サーバ処理 | `memoId`, `createdAt`, `updatedAt` を付与して保存する |
| 成功 | `201 Created` と作成済みメモの JSON |

### 3.4 UI 要件

| ID | 要件 |
|----|------|
| UI-P1-01 | 新規作成用の入力画面（または同等の入力手段）を提供する |
| UI-P1-02 | タイトル・本文・作成者を入力できる |
| UI-P1-03 | 保存操作により API 経由で作成し、成功結果を利用者に分かる形で示す |
| UI-P1-04 | 作成 API 呼び出しは `frontend/src/api/` 経由とする |

### 3.5 例外・分岐

| ID | 条件 | 期待結果 |
|----|------|----------|
| E-P1-01 | 必須フィールド欠落または不正な Body | 4xx とエラーメッセージ。メモは作成されない。UI は失敗が分かる |
| E-P1-02 | DynamoDB／インフラ障害 | 5xx とエラーメッセージ。例外は握りつぶさない |
| E-P1-03 | CORS プリフライト失敗 | ブラウザから作成 API を呼び出せない（防ぎ、許可すること） |

### 3.6 テスト観点（概要）

| ID | 観点 |
|----|------|
| T-P1-01 | 正常な Body で `201` と作成済みメモ（サーバ生成属性含む）が返る |
| T-P1-02 | 必須欠落・不正 Body で 4xx、データが作られない |
| T-P1-03 | UI から入力〜保存まで完了し、結果が分かる |

## 4. Phase 2：一覧表示機能（取得処理〜一覧画面表示まで）

### 4.1 概要

システムが保存済みメモを取得し、一覧画面に表示する。0 件の場合も空状態が分かること。

### 4.2 ユースケース（正常系）

#### UC-P2-01 メモ一覧を見る

| 項目 | 内容 |
|------|------|
| アクター | チームメンバー |
| 事前条件 | なし（0 件でも可）。Phase 1 で作成したメモがあれば一覧に含まれる |
| 基本流れ | 1. 利用者が一覧画面を開く（または再読込する）<br>2. システムが `GET /memos` で一覧を取得する<br>3. 取得結果を一覧画面に表示する |
| 事後条件 | 保存済みメモが画面上で確認できる（0 件なら空状態が分かる） |

### 4.3 API 要件

| 項目 | 要件 |
|------|------|
| メソッド／パス | `GET /memos` |
| クエリ | 初期要件では全件一覧を基本とする（フィルタ・ページングは不明点） |
| 成功 | `200 OK` とメモの配列 JSON |
| 0 件 | `200 OK` と空配列 |

### 4.4 UI 要件

| ID | 要件 |
|----|------|
| UI-P2-01 | メモ一覧画面を提供する |
| UI-P2-02 | 各メモについて、少なくとも識別・内容把握に必要な情報（例: タイトル、作成者、更新日時等）を表示する |
| UI-P2-03 | 0 件時に空状態が分かること |
| UI-P2-04 | 一覧取得 API は `frontend/src/api/` 経由とする |
| UI-P2-05 | Phase 3／4 への導線（詳細・編集・削除への入口）を一覧から辿れること（配置詳細は Plan） |

### 4.5 例外・分岐

| ID | 条件 | 期待結果 |
|----|------|----------|
| E-P2-01 | 一覧 0 件 | `200` + 空配列。UI は空状態を示す |
| E-P2-02 | DynamoDB／インフラ障害 | 5xx とエラーメッセージ。UI は失敗が分かる |
| E-P2-03 | CORS 障害 | ブラウザから一覧 API を呼び出せない（防ぎ、許可すること） |

### 4.6 テスト観点（概要）

| ID | 観点 |
|----|------|
| T-P2-01 | 複数件・0 件それぞれで `200` と配列が返る |
| T-P2-02 | Phase 1 で作成したメモが一覧に含まれる |
| T-P2-03 | UI で一覧表示および空状態が確認できる |

## 5. Phase 3：詳細・更新機能（詳細画面・編集〜更新処理まで）

### 5.1 概要

利用者が既存メモの詳細を確認し、編集画面（または同等）から内容を更新する。サーバは `updatedAt` を更新し、`memoId` / `createdAt` は維持する。

### 5.2 ユースケース（正常系）

#### UC-P3-01 メモ詳細を確認する

| 項目 | 内容 |
|------|------|
| アクター | チームメンバー |
| 事前条件 | 対象メモが存在する |
| 基本流れ | 1. 利用者が一覧等から対象メモを選ぶ<br>2. 詳細画面（または詳細表示）でタイトル・本文・作成者・日時等を確認する |
| 事後条件 | 対象メモの内容が画面上で確認できる |
| 補足 | 単一取得 API（`GET /memos/{memoId}`）の要否は不明点。一覧データ／作成・更新レスポンスの利用も選択肢 |

#### UC-P3-02 メモを更新する

| 項目 | 内容 |
|------|------|
| アクター | チームメンバー |
| 事前条件 | 対象 `memoId` のメモが存在する |
| 基本流れ | 1. 利用者が詳細から編集に進む（または編集画面を開く）<br>2. タイトル・本文・作成者を変更する<br>3. 更新操作を行う<br>4. システムが `PUT /memos/{memoId}` で更新し `updatedAt` を更新する<br>5. 更新結果が詳細／一覧等の UI に反映される |
| 事後条件 | 当該メモが更新後の値になる。`memoId` と `createdAt` は変わらない |

### 5.3 API 要件

| 項目 | 要件 |
|------|------|
| メソッド／パス | `PUT /memos/{memoId}` |
| Path | `memoId` 必須 |
| リクエスト Body | `title`, `body`, `author` 必須の全置換（入出力例は `docs/spec.md` §6.2） |
| サーバ処理 | `updatedAt` を更新。`memoId` / `createdAt` は維持 |
| 成功 | `200 OK` と更新後メモの JSON |
| 不存在 | `404 Not Found` とエラーメッセージ JSON |
| 詳細取得 API | 現行 IaC に `GET /memos/{memoId}` は無い（要否は不明点） |

### 5.4 UI 要件

| ID | 要件 |
|----|------|
| UI-P3-01 | 既存メモの詳細を表示できる |
| UI-P3-02 | 詳細内容を編集し、更新操作できる |
| UI-P3-03 | 更新成功後、表示内容が最新値に同期される |
| UI-P3-04 | 更新 API は `frontend/src/api/` 経由とする |
| UI-P3-05 | 存在しないメモを開こうとした場合、失敗／不在が分かること（取得手段確定後に具体化） |

### 5.5 例外・分岐

| ID | 条件 | 期待結果 |
|----|------|----------|
| E-P3-01 | 対象 `memoId` が存在しない | `404` とエラーメッセージ。UI は不在／失敗が分かる |
| E-P3-02 | 必須欠落または不正な Body | 4xx とエラーメッセージ。既存メモは変更されない |
| E-P3-03 | DynamoDB／インフラ障害 | 5xx とエラーメッセージ。例外は握りつぶさない |
| E-P3-04 | 送られなかったフィールドだけを残す部分更新 | 行わない。`title` / `body` / `author` の全置換（`docs/spec.md` §6.2） |

### 5.6 テスト観点（概要）

| ID | 観点 |
|----|------|
| T-P3-01 | 存在するメモの更新で `200` と更新後内容・新しい `updatedAt` |
| T-P3-02 | 存在しない `memoId` で `404` |
| T-P3-03 | 不正 Body で 4xx、データ不変 |
| T-P3-04 | UI で詳細表示〜編集〜更新反映まで完了する |

## 6. Phase 4：削除機能（削除処理・画面の同期まで）

### 6.1 概要

利用者が既存メモの削除を指示し、システムが永続データを削除する。一覧・詳細等の画面表示から当該メモが消え、同期されること。

### 6.2 ユースケース（正常系）

#### UC-P4-01 メモを削除する

| 項目 | 内容 |
|------|------|
| アクター | チームメンバー |
| 事前条件 | 対象 `memoId` のメモが存在する |
| 基本流れ | 1. 利用者が一覧または詳細から削除を指示する<br>2. システムが `DELETE /memos/{memoId}` で削除する<br>3. 一覧・詳細等の UI から当該メモが消える（再取得またはローカル状態の更新） |
| 事後条件 | 当該 `memoId` のメモが存在しない。画面上も残らない |

### 6.3 API 要件

| 項目 | 要件 |
|------|------|
| メソッド／パス | `DELETE /memos/{memoId}` |
| Path | `memoId` 必須 |
| 成功 | `204 No Content`（ボディなし）。入出力例は `docs/spec.md` §6.2 |
| 不存在 | `404 Not Found` とエラーメッセージ JSON |

### 6.4 UI 要件

| ID | 要件 |
|----|------|
| UI-P4-01 | 一覧または詳細から削除操作できる |
| UI-P4-02 | 削除成功後、一覧（および開いていた詳細）から当該メモが消える |
| UI-P4-03 | 削除 API は `frontend/src/api/` 経由とする |
| UI-P4-04 | 削除前確認（ダイアログ等）の要否は不明点。確定後に必須化する |

### 6.5 例外・分岐

| ID | 条件 | 期待結果 |
|----|------|----------|
| E-P4-01 | 対象 `memoId` が存在しない | `404` とエラーメッセージ。UI は失敗が分かる |
| E-P4-02 | DynamoDB／インフラ障害 | 5xx とエラーメッセージ。画面は誤って消さない（失敗時は同期しない） |
| E-P4-03 | 削除成功後の画面同期漏れ | 受け入れ不可。一覧再表示または状態更新で同期すること |

### 6.6 テスト観点（概要）

| ID | 観点 |
|----|------|
| T-P4-01 | 存在するメモの削除が成功し、再取得で存在しない |
| T-P4-02 | 存在しない `memoId` で `404` |
| T-P4-03 | UI から削除後、一覧に残らない |
| T-P4-04 | 削除失敗時に UI が誤って消えない |

## 8. 非機能要件

| ID | 区分 | 要件 |

| NFR-09 | IaC | ARN／アカウント ID のハードコード禁止 |
| NFR-10 | 可用性・性能の数値目標 | 本要件では未定義（不明点） |
| NFR-11 | 同時編集・楽観ロック | 未定義（不明点） |

## 9. テスト観点（全体・受け入れ）

| ID | 観点 | 内容 |
|----|------|------|
| T-01 | Phase 横断 API | POST / GET / PUT / DELETE が各 Phase 要件どおり動作する |
| T-02 | Phase 横断 UI E2E | 作成→一覧→詳細／更新→削除の一連操作が UI で完了する |
| T-03 | CORS | Vite から SAM Local API を呼び出せる |
| T-04 | ローカル構成 | DynamoDB Local のみを用い、開発中に実アカウント DynamoDB を使わない |
| T-05 | データ整合 | 作成属性、更新後 `updatedAt`、削除後非存在を確認する |
| T-06 | 異常系 | 必須欠落・不存在 ID・障害時の 4xx/5xx |
| T-07 | 回帰手段 | `events/` や単体・統合テストの具体化は Plan 以降 |

受け入れの最低ライン: **T-01, T-02, T-03, T-04** をローカルで満たすこと。
